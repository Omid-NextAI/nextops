# توسعه، گردش‌کار GitHub و انتشار

[English](../en/DEVELOPMENT.md) · [فهرست](INDEX.md)

**وضعیت: قواعد توسعه همراه CI جداشدهٔ برنامه و خودکارسازی محافظت‌شدهٔ لایهٔ package؛ استقرار کامل خودکار تنظیم نشده است.** مبنا:
بخش‌های ۴، ۷، ۸ و ۲۱ تا ۲۶ مشخصات اصلی.

## پیش از پیاده‌سازی بررسی کنید

[AGENTS.md](../../AGENTS.md)، مشخصات اصلی، وضعیت پروژه و کار بعدی خوانده شوند. وضعیت Git، دستورهای پروژه، فایل‌های ثبت‌شده، manifest، فایل قفل، آزمون، migration و تنظیمات استقرار بررسی شوند. تغییرات ثبت‌نشده و پیاده‌سازی موجود حفظ شوند. اسکریپت پیش از اجرا بازبینی و در محیط جدا و بدون اطلاعات ورود عملیاتی آزمایش شود. reset یا clean مخرب، بازنویسی کار دیگران و تغییر تاریخچه مجاز نیست.

مخزن اکنون مرزهای دارای نوعِ سیاست و برنامه، هویت محلی، وضعیت ماندگار و ممیزی در
PostgreSQL، مسیر محدودِ مدل محلی روی CPU، رابط مرورگر دوزبانه و اتصال‌دهنده‌های
فقط‌خواندنی Zabbix و Linux را دارد. انتشارهای کنترل‌شده روی چهار مهمان موجود برای
آزمون کاربر در حال خدمت‌اند؛ شناسهٔ دقیق و نتیجهٔ هر معیار در
[مانیفست انتشار](../status/current-release.yaml) آمده است. برنامهٔ مستقر معیار
گسترش‌یافتهٔ کیفیت پاسخ را نمی‌گذراند و اصلاحِ موجود در کد هنوز مستقر نشده است.
اسکریپت‌های محافظت‌شدهٔ بسته‌های Ubuntu و آزمون بستهٔ آفلاین روی میزکار وجود دارند،
اما هیچ‌کدام مجوز تغییر تازهٔ سرور یا پذیرش تولید نیستند. معماری مرحلهٔ صفر در
۲۱ سپتامبر ۲۰۲۶ پذیرفته شد؛ عملیات و معیارهای بعدی مجوز و بررسی جداگانه می‌خواهند.

برای برش Python فعلی، محیط با `uv sync --extra dev --frozen` نصب و سپس format و Ruff روی
`packages`، `migrations`، `tests`، `scripts` و `deploy/installers`، mypy روی `packages`،
`tests`، `scripts` و `deploy/installers` و در پایان pytest اجرا شود. پذیرش پایگاه به PostgreSQL جدا
در `NEXTOPS_TEST_DATABASE_URL` نیاز دارد؛ suite ردشده با skip، قبولی نیست. `uv.lock` فقط
همراه تغییر بازبینی‌شده تولید و audit وابستگی pin‌شده پیش از انتشار اجرا شود.

## نظم ماژول‌ها

قواعد دامنه از ورودی‌وخروجی چارچوب مستقل باشند. کاربردها به رابط‌ها وابسته‌اند و لایهٔ زیرساخت آن‌ها را پیاده می‌کند. قرارداد میان API، گردش‌کار، سیاست، درگاه و اتصال‌دهنده دارای نوع باشد. Python باید type hint، توضیح روشن API و مدیریت خطا داشته باشد. از منطق تکراری و فایل بسیار بزرگ عامل یا ابزار عمومی پرهیز شود. شناسه‌های کد انگلیسی می‌مانند؛ متن محصول و مستندات کاربر فارسی و انگلیسی دارند.

پوشهٔ کد، manifest و lock زمانی ساخته شوند که پیاده‌سازی واقعی آغاز می‌شود، نه به‌صورت جای‌خالی گمراه‌کننده. رفتار پشتیبانی‌نشده باید خطای صریح بدهد؛ پاسخ شبیه‌سازی‌شده نباید در مسیر عملیاتی موفقیت واقعی جلوه کند.

## تحویل قابل‌بازبینی در GitHub

شاخهٔ کوتاه‌عمر، commit کوچک، معیار پذیرش روشن و pull request به‌کار رود. هر ویژگی به نیاز اولیه و مرحلهٔ مربوط متصل شود. هر تحویل باید راهنمای هر دو زبان، وضعیت، کار بعدی و ردیابی را به‌روز کند. CODEOWNERS و قالب‌ها به بازبینی کمک می‌کنند، اما فعال بودن حفاظت شاخه را ثابت نمی‌کنند. قواعد main و بازبینی باید جداگانه تنظیم و بررسی شوند.

گردش‌کار ثابت `.github/workflows/ci.yml` قالب‌بندی، lint، بررسی نوع، آزمون‌های واحد و
API و مرورگر، اعتبارسنجی سند و پروندهٔ سرور و inference و نصب‌کننده و وضعیت انتشار،
ساخت بسته، ممیزی وابستگی، اسکن همهٔ تاریخچه برای اطلاعات محرمانه و آزمون‌های یکپارچه
روی PostgreSQL 16 و 17 را اجرا می‌کند. دسترسی پیش‌فرض آن فقط‌خواندنی است و اطلاعات
ورود زیرساخت یا مسیر شبکهٔ مدیریت ندارد. تکمیل دادهٔ مجوز در SBOM خصوصی با wheelهای
آماده‌شده، گامی محلی و آفلاین برای گردآوری شاهد است، نه کار CI یا تأیید حقوقی؛ امضای
آفلاین، پذیرش آزمایشگاه و سخت‌افزار، نصب بسته روی سرور در حال خدمت و بررسی حفاظت
شاخه همچنان به اقدام جداگانه نیاز دارند.

کد PR غیرقابل‌اعتماد در worker موقت و جدا، بدون رمز عملیاتی و مسیر شبکهٔ مدیریت اجرا شود. runner دائمی و دارای اختیار روی G10 در اختیار PR دلخواه قرار نگیرد. checkout غیرقابل‌اعتماد با `pull_request_target` و secrets اجرا نشود. آزمون سخت‌افزار معتبر به مسیر جدا، مجوز و محدودیت منابع نیاز دارد.

## شکاف تأییدشدهٔ سیاست مخزن و تنظیم آن توسط مالک

در بررسی فقط‌خواندنی GitHub در ۶ مهر ۱۴۰۵، برای commit با شناسهٔ `de52e43`، شاخهٔ `main`
بدون حفاظت، الزام کنترل وضعیت غیرفعال و فهرست rulesetهای مخزن و قواعد به‌ارث‌رسیده خالی بود.
هر پنج کنترل CI موفق‌اند، اما موفقیت آن‌ها الزامِ ادغام ایجاد نمی‌کند. این مورد بخشی باز از
`release_supply_chain_review` است. اتصال فعلی GitHub اختیار مدیریتی مخزن ندارد؛ تنظیمی تغییر نکرد.

ابتدا مالک باید سیاست را تصویب و بازبین مستقلی با دسترسی مناسب تعیین کند. `CODEOWNERS` اکنون
فقط `AmirMo10` را نام می‌برد؛ معیار تأیید مالک کد نباید غیرقابل‌اجرا شود. مدیر مجاز مخزن می‌تواند
در Settings → Branches قاعدهٔ حفاظت کلاسیک با الگوی `main` بسازد.
[راهنمای تنظیم GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule)
مراحل رابط را توضیح می‌دهد. سیاست پیشنهادی NextOps، نه تصویب‌شده:

- PR و تأیید مستقل الزامی، پس از commit تازه بازبینی تکرار، و پس از تعیین بازبین واجد شرایط،
  تأیید مالک کد نیز الزامی شود.
- شاخه به‌روز باشد و این پنج کنترل از GitHub Actions الزامی شوند: `Quality and unit tests`،
  `PostgreSQL 16 integration`، `PostgreSQL 17 integration`، `Browser acceptance` و `Secret scan`.
  منبع مشاهده‌شده `github-actions` با شناسهٔ برنامهٔ `15368` بود؛ هنگام تنظیم دوباره بررسی شود.
- محدودیت‌ها مدیران را نیز شامل شوند؛ دورزدن، force push و حذف شاخه مجاز نباشد.

مالک با GitHub CLI ازپیش‌تصویب‌شده و احرازهویت‌شده می‌تواند تنظیمات را فقط‌خواندنی بررسی کند:

```powershell
gh api repos/Omid-NextAI/nextops/branches/main --jq '{protected: .protected}'
gh api 'repos/Omid-NextAI/nextops/rulesets?includes_parents=true'
gh api repos/Omid-NextAI/nextops/branches/main/protection
```

مسیر آخر، اختیار خواندن تنظیمات مدیریتی مخزن می‌خواهد؛ خطای مجوز شاهد نبود حفاظت نیست.
[مرجع مجوز REST](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection)
این شرط را مشخص می‌کند. توکن در فرمان، Git یا گفتگو قرار نگیرد. پذیرش به بررسی تنظیم مؤثر و
آزمون مجازِ PR بدون ارتباط با سرورها نیاز دارد که ردِ ادغام در نبود تأیید یا شکست کنترل‌ها را
نشان دهد. با نوشتن مستقیم روی `main` آزمون نکنید. حفاظت مخزن، امضای artifact یا مجوز استقرار نیست.

## انتشار و استقرار

نسخهٔ تأییدشده tag شود و هویت برنامه، وابستگی، کانتینر و مدل، هش و فهرست اجزای نرم‌افزار و مدل ثبت شوند. مالک نسخهٔ تأییدشده را صریحاً برای استقرار انتخاب می‌کند؛ هر push نباید محیط عملیاتی را تغییر دهد. سرور می‌تواند فایل مجاز را از مسیر خروجی دریافت کند و نیازی به SSH عمومی نیست.

پیش از استقرار، هویت فایل، سازگاری تنظیمات، پشتیبان، ترتیب migration و منابع و درگاه‌ها بررسی شوند. پس از آن، سلامت و رفتار مورد انتظار آزموده شود. بازگرداندن برنامه تغییر schema را برنمی‌گرداند؛ سازگاری داده یا مسیر restore آزموده لازم است. بستهٔ آفلاین محصول انتشار صریح است، نه دانلود زمان اجرا.

## هماهنگی عامل‌ها و تعریف پایان کار

کار موازی فقط برای وظیفهٔ مستقل و محدود مناسب است. معمار اصلی مالک قراردادهاست؛ بازبین امنیت مرز اجرا و اطلاعات ورود و تأیید را بررسی می‌کند؛ بازبین CPU/SRE منابع و عملیات را می‌سنجد؛ بازبین محصول و رابط، فارسی طبیعی و جریان کامل کاربر را بررسی می‌کند. در صورت نیاز شاخه یا worktree جدا استفاده شود. چند عامل هم‌زمان migration، قرارداد مشترک یا lock را بازنویسی نکنند. اجرای عامل موازیِ رخ‌نداده ادعا نشود.

کار زمانی تمام است که کد واقعی، آزمون مرزی، فرمان و نتیجهٔ ثبت‌شده، بازبینی امنیت، راهنمای دوزبانه، ردیابی و commit معنادار داشته باشد. mock آزمون تجهیز واقعی نیست. آزمون شکست‌خورده باید اصلاح یا صادقانه گزارش شود، نه برای سبز شدن تضعیف شود.
