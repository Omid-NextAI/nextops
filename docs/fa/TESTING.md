# آزمون، ارزیابی مدل و شواهد انتشار

## نامزد کدیِ حساب‌های محلیِ مدیر — ۴ اکتبر ۲۰۲۶

۵۵۱ آزمون واحد/API/قرارداد موفق و دو مورد وابسته به POSIX در Windows اجرا نشدند. چهارده
آزمون متمرکزِ کاربران با نقش محدود پایگاه و مجموعهٔ کاملِ ۳۳ آزمون یکپارچگی در آزمایشگاه
محلی و جداگانهٔ PostgreSQL 18.6 موفق بودند؛ این نسخهٔ اضافی جای CI نسخه‌های 16/17 نیست.
هر ۲۸ مورد مرورگر موفق بود و یک مورد گردآورندهٔ POSIX اجرا نشد؛ چهار مورد تازهٔ پنل کاربران،
فارسی/انگلیسی، RTL/LTR، موبایل/تم/صفحه‌کلید، مدیر محافظت‌شده، تأیید، پاک‌سازی نشست منقضی،
تعارض بدون تکرار و رد پاسخ دیرهنگام پس از خروج را پوشش می‌دهند. تصاویر فارسیِ رایانه/موبایل
بازبینی دیداری شدند. پاسخ ساختگیِ محلی پذیرش سرور زنده نیست. کاربر عملیاتی، اعتبارنامه،
استقرار، مدل یا منابع تغییر نکردند. [مشخصات](../requirements/USER_MANAGEMENT_SPEC.md)،
CI همان انتشار، پذیرش زنده/آفلاین و بازگشت محافظت‌شده را جدا نگه می‌دارد. commit نخستِ
`e52e26d` هر پنج کار [CI 37211703570](https://github.com/Omid-NextAI/nextops/actions/runs/37211703570)
را گذراند. بازبینی سپس نبود ممیزیِ رد ورودی در FastAPI را یافت؛ اصلاح، JSON، بدنه، مسیر و
پارامتر نامعتبر را به همان تراکنشِ نشست/نقش می‌برد. آزمون‌ها ۲۱ ردِ بدون راز برای مدیر/بیننده
و رد امنِ نبود/نامعتبر بودن/انقضای نشست یا خرابی ممیزی را بررسی می‌کنند. پس از اصلاح، اجرای
محلیِ ۵۵۱ آزمون واحد و ۳۳ آزمون یکپارچگی موفق بود؛ انتشار همچنان CI/بازبینی همان commit و
پذیرش جداگانهٔ زنده می‌خواهد. مجوز پایگاهِ عملیاتی و هیچ حسابی تغییر نکردند.

## پایهٔ محدود به منبعِ MCP-01 — ۴ اکتبر ۲۰۲۶

در رایانهٔ توسعه با Windows، [گام افزودهٔ MCP](../requirements/MULTI_SOURCE_MCP_SPEC.md)،
۲۷ آزمون متمرکز و مجموعهٔ کاملِ بدون پایگاه/مرورگر را گذراند: **۵۵۲ موفق، دو مورد مختص POSIX
اجرا‌نشده و ۴۳ مورد کنارگذاشته‌شده**. موارد کنارگذاشته‌شده قبولی نیستند. Ruff و mypy سخت‌گیرانه
مرز دارای نوع را بررسی می‌کنند. تبادل SDK در حافظه و stdio فرایند فرزند واقعی است؛ داده‌های
زبیکس، مجوز و ممیزی ساختگی‌اند. فرایند stdio فقط محیط حداقلیِ پیش‌فرض SDK و تنظیم رمزگذاری
آزمون را می‌گیرد، نه اطلاعات ورود استقرار. آزمون‌ها شناسهٔ مشابه در دو منبع، ورودی جعلی، ردِ
دامنه/گروه/مقصد، لغو مجوز، شکست ممیزی، نتیجهٔ ناسازگار یا بزرگ، منشأ اصلی، ازدحام، مهلت و پایان
واقعی، اعلان صریحِ لغو و ادامه پس از خرابی را می‌سنجند. آزمون نخستِ لغو شکست خورد، چون لغو
انتظار محلی اعلان پروتکل نمی‌فرستد؛ آزمون اصلاح‌شده اعلان واقعی را ارسال می‌کند. انتظارِ ممیزی
هنگام لغو محافظت‌شده و محدود است؛ گردآوریِ منقضی‌شده پس از پایان درخواست در حال اجرا، خواندن
وابستهٔ تازه‌ای آغاز نمی‌کند.

بازاجرای آزمون پس از آماده‌سازی وابستگی‌ها، بدون اطلاعات ورود عملیاتی:

```text
uv sync --offline --extra dev --extra mcp --frozen
uv run --offline --frozen --extra dev --extra mcp pytest tests/unit/test_source_mcp.py -q
uv run --offline --frozen --extra dev --extra mcp pytest -m "not integration and not browser" -q
uv run --offline --frozen --extra dev --extra mcp ruff format --check packages migrations tests scripts deploy/installers
uv run --offline --frozen --extra dev --extra mcp ruff check packages migrations tests scripts deploy/installers
uv run --offline --frozen --extra dev --extra mcp mypy packages tests scripts deploy/installers
uv run --offline --frozen --extra dev --extra mcp python -X utf8 scripts/check_docs.py
uv run --offline --frozen --extra dev --extra mcp python scripts/check_release_status.py
```

نسخهٔ دقیق `mcp==1.30.0` مجوز MIT دارد. قفل بازبینی‌شده، وابستگی‌های SDK را بدون ارتقای
نسخه‌های پایه می‌افزاید؛ AnyIO در همان نسخهٔ قفل‌شده، وابستگی صریح شد. ابزار ثابتِ
`pip-audit==2.10.1` روی خروجی `uv export --frozen --extra dev --extra mcp --no-emit-project
--no-hashes` آسیب‌پذیری شناخته‌شده‌ای گزارش نکرد. این ممیزی به داده یا شبکه در زمان آماده‌سازی
نیاز دارد؛ عملیات زمان اجرای آفلاین یا اثبات نبود هر آسیب‌پذیری نیست. CI وابستگی MCP را در
کارهای کیفیت، PostgreSQL16/17 و مرورگر صریحاً نصب می‌کند؛ نتیجهٔ CI این تغییر از آزمون محلی
استنباط نمی‌شود.

پذیرش کدیِ تکمیلی برای `d53c2a0`: هر پنج کار در
[CI 37206184531](https://github.com/Omid-NextAI/nextops/actions/runs/37206184531) موفق‌اند؛
آزمون واحد/پروتکل Linux، یکپارچگی واقعیِ موجودِ PostgreSQL16/17، پذیرش مرورگر موجود و Gitleaks
همهٔ تاریخچه را شامل می‌شوند. آزمون پایگاه و مرورگر موجود، مرزهای متصل‌نشدهٔ MCP-02 یا منبع
دوم در رابط زنده را نمی‌پذیرد. محیط تازه و جداگانهٔ Windows، هر ۲۵ وابستگی پایهٔ قفل‌شده را با
`uv pip install --offline --no-index --require-hashes` از wheelهای ازپیش‌آماده‌شده نصب کرد؛
سپس بستهٔ ساخته‌شده با `--no-deps` نصب شد. بارگذاریِ کد نصب‌شدهٔ برنامه/اتصال‌دهنده با مسیر
جدا و `uv pip check`، بدون وجود بستهٔ MCP موفق بودند. SHA-256 بستهٔ wheel:
`24d06413143045bec3e27c2425465a55cd8481b242b0757132c2b7020586ea2c`.
تلاش نخست با cache رجیستریِ تنها، به دلیل فایل‌های غایب شکست خورد و چیزی دانلود نکرد. معرفی
صریحِ مخزن wheel موجود، مشکل مسیر آماده‌سازی را حل کرد. این شاهدِ سازگاری بستهٔ پایه است، نه
آماده‌سازی یا کارکرد مسیر MCP تازه با WAN قطع.

بازبینی پذیرش: جداسازی منابع، رد پیش از دسترسی مقصد، الزام مرز ممیزی، گردآوری محدود، خطای
پالایش‌شدهٔ دارای نوع و آزمون محلیِ پروتکل **موفق‌اند**. اتصال ماندگار PostgreSQL، مالکیت امن
اطلاعات ورود/CA، سقف پیام و گزارش پروتکل، خروجی شبکه و تأیید هویت/انقضا/همهٔ گروه‌ها
**اجرا نشده‌اند** و در MCP-02 هستند. پاسخ تازهٔ زندهٔ دوزبانه در رابط، شروع و شروع دوباره با WAN
قطع، دامنهٔ تولید، بار و بازگشت دقیقِ استقرار **اجرا نشده‌اند** و در MCP-03 هستند. ادعای تازهٔ
رابط یا مدل نداریم؛ قرارداد زبان و زمان موجود حفظ است. مهاجرت پایگاه یا تغییر انتشار زنده رخ
نداده است. کنارگذاشتن مسیر اختیاری، اتصال قبلی را حفظ می‌کند؛ این سازگاری، آزمون بازگشت زندهٔ
MCP نیست.

برنامه/AI زندهٔ `7ce9d29`، اتصال‌دهندهٔ `cdde129`، مدل صرفاً CPU و خاموش بودن استدلال ثابت‌اند.
شاهد زندهٔ تاریخ‌دار در ادامه حفظ شده، اما خودکار به منبع تازه تعمیم داده نمی‌شود.

## چرخهٔ کنترل محدودِ راهنمای تشخیصی — ۴ اکتبر ۲۰۲۶

نامزد `7ce9d2969d6bea8186783c5ce04a1c93be811a97`، تعداد ۵۲۴ آزمون محلیِ واحد/API/قرارداد،
lint، بررسی سخت‌گیرانهٔ نوع و کنترل ۱۲۶ سند/۳۸ جفت زبانی را گذراند. دو آزمون POSIX در
Windows اجرا نشدند؛ ۴۳ آزمون پایگاه/مرورگر از اجرای محلی کنار گذاشته شدند. هر پنج کار در
[CI 37185116587](https://github.com/Omid-NextAI/nextops/actions/runs/37185116587)، شامل پایگاه
واقعی PostgreSQL16/17، مرورگر و Gitleaks موفق‌اند. نصب تازهٔ هش‌قفل و بدون index در WSL
با Ubuntu24.04 و هر دو مهمان موجود، تطبیق وابستگی و کدِ نصب‌شده با کاربر غیرریشه را گذراند.
SHA-256 بستهٔ wheel: `8dfecb6b9a422ad0a2be3240797cbad05f15f46d52aa84973d7031780be66816`؛
هش کدِ نصب‌شده: `32fd417abde79c6f10fbe6dd74cf6eadde8be3e0df3012c636763a1e81e7cd17`.
پذیرش هماهنگِ زنده موفق شد و برنامه و AI نسخهٔ `nextops-0.1.0-7ce9d29` برای کاربران کنترل‌شده
دوباره مستقر شدند. آزمون‌های مرورگر تازهٔ Edge با TLS معتبر، ۱۳ مورد نخست، ۱۳ مورد آفلاین،
چهار مورد پس از بازگشت دقیق به69 و ۱۵ مورد نهایی را گذراندند: **در مجموع ۴۵ مورد کارکردی**،
شامل ادامهٔ گفت‌وگوی دوزبانه، شاهد تازهٔ هدف مجاز AI، محدودیت هدف غایب، هدایت پرسش آمیخته با
وضعیت واقعی و دو بررسی واقعیِ نمایش پاسخ جایگزین و بارگذاری دوبارهٔ آن. بررسی فقط‌خواندنیِ
پایگاه، **۳۶ ممیزیِ تکمیل بدون متن و نه جفت شاهد زنده/هش اصلی** را تطبیق داد؛ ردِ عدم تطابق
پرسش و هدف نیز ممیزی شد. فقط گفت‌وگوهای آزمایشیِ متعلق به همین ابزار و نشست‌های موقت آن حذف
یا باطل شدند. خروجیِ مثال‌های محدود جداگانه بازبینی شد: محدودیتِ برنامه‌ای پذیرفته شد، نه
درستیِ عمومیِ متن خام مدل.

در آزمون چهار درخواستِ همین نسخه، یک درخواست فعال و دو درخواست در صف مشاهده شد: پاسخ200
در ۸٫۰۲۲ ثانیه، دو خطای مهلت صف504 در ۵٫۰۱۴ و ۵٫۰۱۵ ثانیه و ردِ درخواست چهارم با429 در
۰٫۰۱۰ ثانیه. پاسخ تازهٔ پس از آن در ۱٫۰۲۹ ثانیه تکمیل و هر دو شمارنده صفر شدند. این شاهدِ
پذیرش و ادامهٔ محدود است، نه آزمون بار پایدار. در هر چهار مهمان، سیاست خروجی موقتِ همین آزمون،
IPv4/IPv6 بیرونی و پراکسی نصب را مسدود و شبکهٔ مدیریت داخلی را حفظ کرد. دارایی‌های مرورگر تازه،
ورود، تولید محلیِ دوزبانه و شاهد واقعاً تازهٔ Zabbix زیر این منع موفق بودند؛ منع پیش و پس از
آزمون بررسی شد. فرایند مدل، API هوش مصنوعی و برنامه زیر منع دوباره شروع شدند؛ آمادگی مدل/API
پس از ۲۷ ثانیه و برنامه پس از دو ثانیه برقرار شد. پرسش وضعیت AI به دو زبان ۶۹٫۷۳۴ و ۷۱٫۴۳۷
ثانیه طول کشید. این منع واقعیِ WAN/پراکسی در سرورها و شروع دوبارهٔ فرایند است، نه قطع روتر،
راه‌اندازی دوبارهٔ VM یا شروع سردِ بدون cache. شروع PostgreSQL، اتصال و Zabbix برای این کد
تکرار نشد.

پیش از استقرار دوبارهٔ محافظت‌شده، بازگشت دقیقِ دو لایه به69، چهار پاسخ تازه و چهار ممیزیِ
دوزبانه را گذراند. پرسش وضعیت AI در مرحلهٔ نهایی ۶۳٫۷۰۳ و ۶۹٫۲۶۶ ثانیه طول کشید. بسته و کد
دقیق، هش مدل/runtime، سلامت سرویس‌ها و صفر بودن شمارنده‌ها دوباره بررسی شدند. فقط جدول و
زمان‌سنج پاک‌سازیِ شبکهٔ همین آزمون و زمان‌سنج‌های بازگشت نهایی حذف یا متوقف شدند؛ نسخه‌های
محافظت‌شدهٔ قبلی، گزارش خام و سایر سیاست‌های شبکه محفوظ‌اند. مشاهدهٔ جاری مهمان، ۸۰ vCPU و
۱۲۸۷۶۹ MiB حافظهٔ قابل‌استفاده بود؛ این چرخه منابع را تغییر نداد و بهینگی NUMA ادعا نمی‌شود.
مدل Qwen3.5-35B-A3B با زمینهٔ16384، شانزده رشته، یک جایگاه و استدلال خاموش ثابت است.
فرادادهٔ توصیفیِ گفت‌وگوی گسترش‌یافته با کد7ce تطبیق دارد و پیش‌فرض ۳۸۴توکنیِ مدل را از
قرارداد ۱۲۸توکنیِ درخواستِ لایهٔ نصب‌شده اما غیرفعال جدا می‌کند؛ هیچ تنظیمِ زنده تغییر نکرد.
پاسخ معمولیِ آفلاین موفق و استدلال فعال اجرا‌نشده است. آزمون پس از ثبت شاهد، شناسهٔ قدیمی و
یکی‌گرفتنِ بودجهٔ مدل و درخواست را یافت. اصلاحِ رکورد و آزمون سخت‌گیرانهٔ بودجه/شناسه، ۵۲۵
آزمون محلی را موفق کرد (دو مورد Windows اجرا‌نشده؛ ۴۳ مورد کنارگذاشته‌شده)، نه با تضعیف شرط
آزمون یا ساخت بستهٔ تازهٔ در حال خدمت.

در چرخهٔ محدودِ مجازِ مالک، چهار تلاش ناموفق حفظ شدند: b80758e سیزده مورد کارکردی، چهار
ممیزی گفت‌وگو/سه هش شاهد و ادامهٔ صف را گذراند، ولی در فارسی از TLS سلامت شبکه را نتیجه
گرفت؛ f05e222 پس از اصلاح ابزار، سیزده مورد کارکردی را گذراند، اما نبود دادهٔ تازه را علت
اختلال گردآوری دانست؛ e0a0fd8 سیزده مورد و کنترل دادهٔ قدیمی را گذراند، ولی از اعتبارسنجی
نام، حل نام DNS را نتیجه گرفت؛ 1a934e9 سیزده مورد، ده ممیزی/سه هش و پذیرش محدودِ صف را
گذراند، ولی پرسشِ گواهی/نام بدون واژهٔ TLS، کنترل را نگرفت. پیش از نامزد بعدی، هر کد دقیقاً
به برنامه/AI نسخهٔ69 بازگشت.
ابزار خصوصی نیز یک بار به‌اشتباه برای ایجاد گفت‌وگو HTTP200 خواست؛ قرارداد موجود HTTP201
است. گزارش متوقف‌شدهٔ هفت‌موردی حفظ است، نه خطای برنامه یا پذیرش موفق. یک گفت‌وگوی خالیِ
آزمایشیِ احتمالاً رهگیری‌نشده دست‌نخورده ماند تا ردیفِ اثبات‌نشدهٔ کاربر حذف نشود. گزارش خام
و علت شکست خصوصی‌اند؛ شکست فنیِ گسترده‌ترِ capability-v2 در PR51 نه مستقر و نه حذف شده است.

این گام، قصدِ فرضیِ محدود، ردِ ادعاهای بررسی‌شدهٔ انتقال/سلامت کلی و محدودیتِ آشکارا برنامه‌ای
برای نتیجه‌گیریِ فرض TLS و مثالِ بدون دادهٔ تازه را اضافه می‌کند. پاسخ‌ها `deterministic_fallback`
و `model_only` هستند، نه شاهد تازه یا موفقیتِ درستیِ خام مدل. راهنمای عمومی، ردِ وضعیت واقعی/
اجرای عملیات، هویت منبع، علت پایان خام و مرزِ سیاست/اعتبارنامه حفظ‌اند؛ هیچ کد مدل اجرا نمی‌شود.
مدل، runtime، صف، مهلت، سهم حافظه، پراکسی، پایگاه و دارایی‌های OCS ثابت‌اند و استدلال خاموش است.
شروع دوبارهٔ VM همین کد، بار پایدار، کیفیت نزدیک ظرفیت کامل زمینه و تأیید معنای عمومی با این
چرخهٔ محدود پذیرفته نمی‌شوند. رکوردهای تاریخ‌دارِ زیر تاریخی‌اند و به‌طور ضمنی منتقل نمی‌شوند.

نخستین استقرار زندهٔ `089e3ad` در آزمون شش‌پرسشیِ احرازهویت‌شده شکست خورد، زیرا طرح‌وارهٔ
HTTP استنتاج، فیلد `purpose` را نداشت. هر دو نقش به ترتیب معکوس وابستگی به نسخهٔ قبلی برگشتند؛
شش پاسخ نسخهٔ قبلی HTTP 200 و خروج 204 گرفت، ولی چهار انتظارِ شناخته‌شدهٔ پایش و تمرکز بر فایل
همچنان شکست خوردند. این نتیجه، موفقیتِ بازگشت محدود است، نه موفقیت معیار معنایی نسخهٔ قبلی.
اصلاح، پنج آزمون مرز HTTP می‌افزاید که نوع عمومی/شاهد، فارسی/انگلیسی، پیش‌فرض قدیمی، نوع
نامعتبر و نبود احراز هویت سرویس را پوشش می‌دهند.

روی میزکار Windows، فرمان `uv run --offline pytest -m "not integration and not browser" -q`
با ۲۵۲ آزمون موفق و دو موردِ مختص POSIX که اجرا نشدند، پایان یافت. بررسی سخت‌گیرانهٔ نوع‌ها برای
۹۲ فایل، lint و قالب‌بندی موفق بود. پنج آزمون موجودِ Playwright با دادهٔ آزمایشی و مرورگرهای
محلیِ ازقبل‌آماده موفق شدند؛ این نتیجه، آزمون مرورگرِ سرور یا قطع واقعی WAN نیست. اعتبارسنجی
UTF-8 برای ۱۲۰ فایل Markdown و ۳۶ جفت زبانی و نیز بررسی وضعیت انتشار و هر دو رکورد مدل موفق
بودند. قفل وابستگی تغییر نکرد. پایان کامل پرسش در هر سه مسیر، ردِ تنظیم جعلیِ نوع پردازش یا
مدل توسط کاربر، تفکیک دستور عمومی و شاهد، شناسهٔ دقیق مدل بزرگ‌تر و تثبیت منبع آزموده شدند.
هشت تولید ساختگیِ متوالی روی 8B کامل شدند، اما عبارت فارسی و حذف نام منبع همچنان یافته‌اند،
نه موفقیت کیفیت. در این گامِ کد، انتشار مستقر و شکست معیار معنایی آن تغییر نکرده‌اند.

## احراز صلاحیت وابسته به نسخهٔ دقیق برنامه — قرارداد مانیفست

در مانیفست انتشار، بخش عمومی `acceptance_gates` شواهد تاریخ‌دار آزمون‌های کنترل‌شدهٔ پیشین را
نگه می‌دارد؛ موفقیت آن‌ها خودبه‌خود به نسخهٔ تازهٔ برنامه منتقل نمی‌شود. نسخهٔ دوم طرح‌واره، بخش
الزامیِ `current_application_qualification` را افزوده است که شناسهٔ انتشار و commit آن باید با
برنامهٔ مستقر یکسان باشد. برای `nextops-0.1.0-01755d1`، کارکرد زندهٔ محدود موفق است؛ اما معیار
گسترش‌یافتهٔ معناییِ دوزبانه با پرسش‌های ساختگی اکنون `failed` است و نمونهٔ دقیقِ کنارگذاشته‌شدهٔ
مالک هنوز بررسی نشده است. بازگشت همین انتشار، قطع WAN در سمت سرور و راه‌اندازی دوبارهٔ ماشین و
شروع سرد، `not_run` هستند. اعتبارسنج، نبود هر دروازه یا ناسازگاریِ
شناسهٔ انتشار را رد می‌کند. این اصلاحِ ثبت شواهد است، نه آزمون زندهٔ تازه یا پذیرش تولید.

اعتبارسنجِ وضعیت انتشار همچنین ادعای موفقیت تولید را رد می‌کند، مگر آنکه وضعیت استقرار، همهٔ
دروازه‌های نسخهٔ جاری برنامه و انتشار، و شرایط ساختاری پروفایل بازیابی با یکدیگر سازگار باشند.
این کنترل فقط تناقض در مانیفست را آشکار می‌کند؛ استقلال فیزیکی مقصد، بازیابی واقعی یا تأیید
انسانی را ثابت نمی‌کند. برای بازبینی تولید باید فرمان
`python scripts/check_recovery_profile.py --require-qualified` جداگانه اجرا و شواهد خصوصیِ
بازیابی و تصویب‌ها بررسی شوند. پروفایل ثبت‌شده همچنان مسدود است.

## گردآوری پاسخ برای بازبینی معناییِ انتشار دقیق — ابزار کد، نه پذیرش

در ۴ مهر ۱۴۰۵، شش پرسش ساختگیِ فارسی و انگلیسی از مسیر خصوصیِ برنامهٔ در حال خدمت فرستاده شد؛
هر شش پاسخ HTTP 200 و خروج سمت سرور 204 بود. سلام‌ها کوتاه و بدون محتوای پایش بودند. دو پرسش
دربارهٔ میزبان‌های خارج از دسترس به‌جای بیان روشنِ محدودیت دامنه، خلاصهٔ کلی زبیکس گرفتند؛ دو
پرسش «فقط فایل» نیز `overview` تشخیص داده شدند و دادهٔ نامرتبط آوردند. زمان پاسخ حدود ۶ تا ۴۹
ثانیه بود. گزارش کامل، پرسش‌ها، پاسخ‌ها و شواهد عملیاتی در پوشهٔ خصوصی ارزیابی مانده‌اند، نه در
Git. ابزار، شناسهٔ کدِ پشت سرویس را مستقلاً تأیید نکرد. این شکست معنایی، پذیرش مسیر زندهٔ کنونی
را رد می‌کند؛ اصلاح فعلاً فقط در کد است و پیش از هر ادعای پذیرش باید با استقرار محافظت‌شده و
آزمون زندهٔ دوباره سنجیده شود. این شش نمونهٔ ساختگی جای نمونهٔ دقیقِ پالایش‌شدهٔ مالک یا مجموعهٔ
کامل پرسش‌های کنارگذاشته‌شده را نمی‌گیرند.

در اصلاحی که هنوز مستقر نشده، فرمانِ
`uv run python scripts/compute_app_code_digest.py <wheel>` هش کد برنامه و فایل‌های محلیِ رابط
را از wheel نامزد، بدون اینترنت محاسبه می‌کند. هش کاملِ خودِ wheel باید جداگانه با رکورد خصوصیِ
انتشار مصوب تطبیق داده شود. پس از استقرار نامزد، هر پاسخ موفقِ احرازهویت‌شده سرآیند
`X-NextOps-App-Code-SHA256` را خواهد داشت. مقدار مورد انتظار با گزینهٔ
`--expected-app-code-sha256` به ابزار خصوصیِ گردآوری داده می‌شود؛ نبود یا ناسازگاریِ سرآیند،
فرمان را پس از حفظ گزارش و تلاش برای خروج از نشست ناموفق می‌کند. در آزمایشگاه میزکار، هش یک
wheel واقعیِ ساخته‌شده به‌صورت آفلاین با هش درخت کدِ فعلی یکسان بود. انتشارِ در حال خدمت این
سرآیند را ندارد؛ بنابراین آزمون زنده‌ای موفق نشده است. این هش، وابستگی‌ها، migration، محیط
اجرای مدل، خودِ مدل، امضای انتشار یا سلامت میزبان را پوشش نمی‌دهد؛ مقدار
`release_identity_verified_by_this_script` همچنان `false` است و بازبین باید رکورد استقرار و
هر پاسخ را با شواهد آن جداگانه بسنجد.

در ۵ مهر ۱۴۰۵، wheel نامزد تازه از commit ادغام‌شدهٔ `d973785` به‌صورت آفلاین ساخته شد.
`Get-FileHash` در Windows و `sha256sum` در Ubuntu برای کل فایل، هش یکسانِ
`80fe318f838c8395c6ca29f6f0e6a806f6884b81df5a5c72cae719c2d9ed7b40` را ثبت کردند.
هش کدِ wheel و بستهٔ نصب‌شده در محیط تازهٔ Ubuntu 24.04.5 روی WSL2 نیز هر دو
`213b3fad8859d7afc005b189a568306f9c51443531c3232d86e966721fa84e46` بود. ابزار
خصوصیِ SBOM، مجموعهٔ تغییرنیافتهٔ ۲۵ wheel لینوکسی را دوباره با `uv.lock` سنجید؛ ۲۴ وابستگیِ
قابل‌اعمال در Linux با `--no-index --require-hashes` و سپس wheel برنامه با
`--no-index --no-deps` نصب شدند. `pip check` و واردکردن API برنامه، `psycopg`،
`pydantic_core` و `greenlet` موفق بود. نامزد و رکورد دقیقِ فرمان‌ها و شواهد بیرون Git مانده‌اند.
این فقط آزمون بسته و نصب در میزکار است: WAN قطع نشد، سرویس مدل یا پایگاه داده آغاز نشد و انتشار
مستقر یا شکست معیار کیفیت پاسخ آن تغییر نکرد. wheel امضا و برای استقرار تصویب نشده است.

در ۶ مهر ۱۴۰۵، هر پنج کار CI در PR شمارهٔ ۲۸ موفق شد و تغییر در `b868e3e` ادغام شد. wheel
تازه با `uv build --offline --no-sources --wheel` ساخته شد و Windows و Ubuntu مستقلاً
هش کل فایل را با مقدار
`dba186458c7b12ea56bfed7e8dde4be761cd5d792feabb34be0543bbf0e6991d` تطبیق دادند.
هش کدِ درخت منبع، wheel، بستهٔ نصب‌شده در محیط تازهٔ Ubuntu 24.04.5 و مقدار هنگام آغاز API
همگی `c8a3b566ba501dd15c904555f00f5589499f746655d489840502c3d94599ebd5` بود. مجموعهٔ
تغییرنیافتهٔ wheelهای Linux دوباره با `uv.lock` سنجیده شد؛ ۲۴ بستهٔ قابل‌اعمال و برنامه بدون
فهرست بسته‌ها نصب شدند و `pip check` و واردکردن API و ماژول‌های بومی موفق بود. ده آزمون ساختگی
در بستهٔ نصب‌شده، ردِ پاسخ نامرتبط به سلام، حفظ سلام دوزبانهٔ مرتبط، هدایتِ پرسشِ سلام همراه با
وضعیت و کنترل خروجیِ ناتمام را سنجیدند؛ هر دو اعلان جایگزین نیز در فایل‌های رابط وجود داشتند.
فرایند آزمون و رکورد دقیق بیرون Git مانده‌اند. WSL دربارهٔ منتقل‌نشدن پراکسی localhost در حالت
NAT هشدار داد؛ شبکه تغییر نکرد و WAN قطع نشد. انتقال به سرور، سرویس، پایگاه، تولید مدل، پاسخ
مرورگر، بازگشت یا معیار تولید آزموده نشد. wheel همچنان بدون امضا و فاقد تصویب استقرار است؛
معیار معناییِ انتشارِ در حال خدمت `failed` باقی می‌ماند.

ابزار `scripts/evaluate_live_app_semantics.py` حداکثر دوازده پرسش تازه را از مسیر احرازهویت‌شدهٔ
HTTPS خصوصی برنامه ثبت می‌کند. ورودی آن ارجاع محافظت‌شدهٔ نشانی، فایل ورود، گواهی CA محلی و
مجموعهٔ JSON خصوصی شامل `id`، `mode` (`general`، `monitoring` یا `incident`)، `locale`،
`question` و برای بررسی رخداد، `target_id` مجاز است. پراکسی و تغییرمسیر را غیرفعال می‌کند، TLS
را می‌سنجد، زمان و اندازهٔ پاسخ را محدود می‌کند، پاسخ و شواهد همراهش را در گزارش خصوصیِ تازه
می‌نویسد و برای خروج سمت سرور تلاش می‌کند. توکن و متن پاسخ در ترمینال چاپ نمی‌شود. این ابزار
شناسهٔ انتشارِ اعلام‌شده را مستقلاً تأیید یا درستی معنایی را داوری نمی‌کند و هیچ معیار پذیرشی را
موفق اعلام نمی‌کند؛ بازبین باید هر پاسخ را با پرسش، منبع/زمان/دامنهٔ شاهد و محدودیت‌ها بسنجد.
پرسش‌ها و گزارش‌ها بیرون Git بمانند و آزمون فقط با حساب و پنجرهٔ مجاز انجام شود؛ این آزمون بار نیست.
ابزار مسیر گزارشِ داخل مخزن را رد می‌کند. دسترسی پوشهٔ ورودی و خروجی در سیستم‌عامل محدود شود.

هر مورد می‌تواند انتظارهای محدود و واژگانی برای تمرکز پاسخ، وضعیت صحت، یک کد محدودیتِ الزامی، و
عبارت‌های لازم یا ممنوع در پاسخ داشته باشد؛ نام ناشناختهٔ انتظار رد می‌شود. گزارش، کدهای موفقیت
و شکست را بدون چاپ متن پاسخ ثبت می‌کند و در صورت شکست یک انتظارِ تعریف‌شده، فرمان پس از خروج از
نشست با خطا پایان می‌یابد. اکنون اگر حتی یک پرسش انتظارِ تعریف‌شده نداشته باشد، یا پاسخ فقط
تکرارِ یک پرسشِ بلند باشد، فرمان با خطا پایان می‌یابد؛ در هر دو حالت، گزارش حفظ و خروج از نشست پیگیری
می‌شود. خروجِ موفق تنها به معنی گذر کنترل‌های خودکار و تکمیل درخواست‌هاست، نه اثبات درستی پاسخ،
ارتباط معنایی یا شناسهٔ انتشارِ پشت سرویس. بازبینی آفلاینِ گزارش خصوصیِ پیشین، با انتظارهای
تعریف‌شده، دو سلام را موفق و دو پرسش فهرست میزبان و دو پرسش «فقط فایل» را ناموفق نشان داد؛
برای این بازبینی درخواست تازه‌ای
به سرورها نرفت.

یک بستهٔ wheel خالص پایتون از commit شمارهٔ `42b35d8` به‌صورت آفلاین ساخته شد و فایل‌های اصلاح‌شدهٔ
درون آن با کد منبع یکسان بودند. نصب آفلاین در محیط تازهٔ پایتون ۳٫۱۲ روی همین میزکار Windows
به‌دلیل نبود wheel وابستگی‌ها در حافظهٔ محلی شکست خورد. این نتیجه، wheelhouse لینوکسیِ قبلاً
هش‌شده روی سرور برنامه را نه می‌آزماید و نه رد می‌کند؛ این wheel نیز بستهٔ کامل، امضاشده و آمادهٔ
استقرار نیست.

در آماده‌سازیِ متصلِ بعدی، از قفلِ تغییرنیافتهٔ محیط اجرا دو مجموعهٔ خصوصی و دارای هش، هرکدام
با ۲۵ wheel برای Linux و Windows ساخته شد. هر فایل با نام و SHA-256 ثبت‌شده در `uv.lock` یکسان
بود و مجموعهٔ لینوکس بدون دسترسی به فهرست بسته‌ها دوباره حل شد. در محیط تازهٔ پایتون ۳٫۱۲ روی
Windows، وابستگی‌های کنترل‌شده با هش و wheel برنامه بدون فهرست بسته‌ها نصب شدند؛ `pip check`،
واردکردن ماژول‌های API و وجود فایل رابط موفق بودند. این نتیجه شکست پیشینِ حافظهٔ محلیِ میزکار
را برطرف می‌کند، ولی چون WSL2 توزیع لینوکسیِ نصب‌شده ندارد، نصب واقعی روی Ubuntu آزموده نشده
است. SBOM خصوصیِ CycloneDX 1.5 دارای ۲۵ جزء و فاقد دادهٔ مجوز است و ابزار تولید آن آزمایشی است.
این آماده‌سازی و آزمون Windows، بستهٔ لینوکس، سیاست مجوز، امضای انتشار، برنامهٔ مستقر یا دروازهٔ
تولید را تأیید نمی‌کنند.

در ۵ مهر ۱۴۰۵، نصب توزیع Ubuntu 24.04 در WSL2 از هر دو روش معمول و دریافت مستقیم، پیش از
نصب با خطای `Wsl/InstallDistro/0x80072f78` (پاسخ نامعتبر یا ناشناختهٔ سرور) شکست خورد؛
WSL هنوز توزیعی ندارد. ابزار Docker هم به سرویس محلیِ آن وصل نشد. بررسی خصوصیِ ۲۵
wheel لینوکس نشان داد همهٔ آن‌ها اظهارنامه و فایل مجوز دارند: ۱۳ مورد MIT، شش مورد
BSD-3-Clause، دو مورد LGPL-3.0-only و از Apache-2.0، MIT AND PSF-2.0، MIT-0 و
PSF-2.0 هرکدام یک مورد. این‌ها داده‌های خودِ بسته‌ها هستند، نه تأیید حقوقی یا تکمیل
دادهٔ مجوز در SBOM. پس از آن، نصب روی Ubuntu، تصمیم مجوز یا آزمون سرور انجام نشد.

مالک روشن کرد که فقط بازیابی از snapshot ماشین ESXi را آزموده است. گزارش تاریخ‌دار آن در این
بازبینی بررسی نشده و معیار پشتیبان مستقل، WAL/PITR یا بازیابی ایزولهٔ پایگاه را کامل نمی‌کند.

داد؛ قدیمی‌ترین ping فقط ۴۸ ثانیه عمر داشت. item مربوط به `agent.version` هر یک ساعت اجرا می‌شود

Authorization رد می‌کنند. نتیجهٔ محلی: ۱۶۱ آزمون موفق، یک آزمون مخصوص POSIX کنارگذاشته و نه آزمون
یکپارچگی PostgreSQL در این محیط انتخاب‌نشده؛ Ruff، mypy سخت‌گیرانه و Bandit موفق بودند. اجرای

دیوارهٔ آتش AI، تونل تازه‌راه‌اندازی‌شدهٔ برنامه به AI دوباره به آمادگی مدل محلی رسید.

حذف کرده بود. اکنون درخواست مستقیم HTTPS روی IPv4 از پوستهٔ مدیریتی هر چهار مهمان موفق است؛ IPv6

`IPAddressDeny=any` با استثنای loopback دارند. اتصال‌دهنده نیز اکنون همهٔ مقصدها به‌جز loopback و
شبکهٔ داخلیِ بررسی‌شدهٔ استقرار را رد می‌کند، اما فرایندهای عمومی میزبان زیر منع دائمی اینترنت
در سطح میزبان نیستند. در نتیجه پذیرش‌های آفلاینِ مشخص‌شده همچنان شاهد تاریخی معتبر دارند، ولی
سیاست دائمی خروجی کل میزبان ناقص است. بدون فهرست معتبر مقصدهای DNS، زمان و پراکسی نگه‌داری و راه

حفاظ timer بازگشت سالم راه‌اندازی شد. سپس چهار درخواست تازهٔ رخداد در Edge احرازهویت‌شده، یکی

مقصد بدون قواعد پاسخ HTTP 200 داد؛ این آزمون منفی سرویس اصلی را تغییر نداد. سرویس هشدار تازه
نداشت و timer بازگشت لغو شد. این شاهد مربوط به مرز فرایند اتصال‌دهنده است، نه دیوارهٔ خروجی

SHA-256 در پوشهٔ بازگشتِ فقط‌خواندنی برای root روی همان میزبان ثبت شد. خوشه‌های PostgreSQL برنامه

بایگانی دقیق برنامهٔ مستقر پیش از بررسی هش شد. Syft نسخهٔ `1.52.0` با digest تأییدشده، SBOMهای

## شواهد تاریخی استقرار کنترل‌شدهٔ گام 2A

قرارداد محدود «بافت رخداد» در مرزهای API اتصال‌دهنده و برنامه پیاده‌سازی و آزموده شده است.
آزمون‌های قطعی، همان میزبان پیکربندی‌شده، اعتبارسنجی بازهٔ ۱۵ تا ۱۴۴۰ دقیقه، پارامترهای ثابت

نتیجهٔ ناقص، احرازهویت bearer و خطای امن وابستگی را بررسی می‌کنند. در تغییر
`phase2a-incident-context-20260923-01`، انتشار تغییرناپذیر `nextops-0.1.0-1ab6586` روی برنامه و
اتصال‌دهنده مستقر و checksum آن تأیید شد. نقش خوانشگر دقیقاً با `history.get` و `event.get` گسترش
یافت و روش‌های نامرتبط همچنان رد می‌شوند. یک درخواست زنده از Zabbix 7.0.30، هشت سنجهٔ جاری، ۳۲

رد bearer نامعتبر در اتصال‌دهنده، رد نشست نامعتبر در برنامه، تونل محافظت‌شدهٔ برنامه به
اتصال‌دهنده، بازگشت و بازگردانی انتشار هر دو سرویس و بازگشت و بازگردانی نقش خوانشگر موفق بودند.

یک جدول موقت و جداگانهٔ nftables، همراه زمان‌سنج بازگشت خودکار پنج‌دقیقه‌ای، دسترسی مستقیم IPv4 و
IPv6 به WAN را روی مهمان‌های برنامه، اتصال‌دهنده و Zabbix بست؛ در همان زمان درخواست زندهٔ بافت
رخداد از مسیر خصوصی مصوب موفق ماند. سپس جدول و زمان‌سنج حذف شدند، دسترسی مستقیم TCP روی IPv4
بازگشت، هر چهار مهمان در وضعیت `running` و بدون واحد خراب یا نیاز به راه‌اندازی مجدد بودند. این
شاهد، مسیر سروری 2A را با WAN مسدود ثابت می‌کند، نه مرورگر تازه یا شروع سرد را. استفاده با نشست
احرازهویت‌شدهٔ مرورگر، پیوند ماندگار مدل و ممیزی، و راه‌اندازی مجدد VM برای 2A در آن نقطه
`not_run` بودند. رکورد جاری بالا وضعیت پیاده‌سازی را جایگزین می‌کند و شاهد تاریخ‌دار را حفظ
می‌نماید.

## صلاحیت‌سنجی تکمیل کنترل‌شدهٔ مرحلهٔ ۱

[گزارش تاریخ‌دار تکمیل](STAGE_1_COMPLETION_REPORT.md) خلاصهٔ شواهد است. ابزار مرورگر از context

ورود، هر دو جهت متن، حالت عمومی و پایش، منشأ شاهد، شناسه‌های ماندگار، خروج و الزام ورود در برگهٔ
تازه موفق بودند.

پوشش منبع برای خروج سمت سرور اکنون رد درخواست بدون bearer، لغو دقیق و دارای شناسهٔ هم‌بستگی،
پاسخ خالی و idempotent، محفوظ‌ماندن نشست دیگر همان هویت، ثبت یک رویداد ممیزی پالایش‌شده و
فقط‌افزودنی، حذف `sessionStorage` مرورگر و بازگشت بومی‌شده به ورود را بررسی می‌کند. کنترل PostgreSQL
در ماتریس CI نسخه‌های 16 و 17 اجرا می‌شود. این نتیجه فقط زمانی پذیرش استقرار خواهد بود که توکن
واقعی پیشین در یک مسیر محافظت‌شده رد و رویداد ممیزی متناظر تأیید شود.

برنامه از `13a3369` به `fde27bd` بازگشت و دوباره به نسخهٔ جاری منتقل شد. نسخه‌های محافظت‌شده و
هم‌هشِ محیط اجرا و مدل از طریق پیوندهای پایدار انتخاب شدند، API واقعی NextOps پاسخ تولید کرد و سپس
مسیرهای اصلی بازگردانده شدند. لغو زنده ظرفیت را آزاد کرد؛ قطع فراهم‌کننده در برنامه خطای پالایش‌شده
و قابل‌تکرار `503` ساخت؛ مقصد موقتِ مدل مفقود یا خراب به‌صورت امن متوقف شد؛ و مقصد ۶۴ MiB ایزوله
برای کپی artifact با `ENOSPC` شکست خورد، بی‌آنکه مدل سرویس‌دهنده تغییر کند.

پروفایل پنج‌دقیقه‌ای با دو کارخواه، ۹۹ درخواست، ۹۸ موفقیت و یک پایان مهلت محدود داشت. p50/p95/
بیشینهٔ زمان کل ۶٫۰۹۵/۶٫۱۱۴/۸٫۵۲۰ ثانیه بود، بیشینهٔ حافظهٔ مشاهده‌شدهٔ سرویس
4,885,475,328 بایت و بیشینهٔ زمان‌بند یک درخواست فعال و یک درخواست در صف بود. TTFT در API
غیرجریانی فعلی قابل مشاهده نیست. هر دو dump منطقی دارای checksum در خوشه‌های موقت PostgreSQL
16.15 و فقط از طریق socket بازیابی شدند؛ schema، حفاظت ممیزی برنامه، پیکربندی و شمار تاریخچهٔ
Zabbix پیش از پاک‌سازی کامل تأیید شدند. این نتیجه روش بازیابی منطقی را ثابت می‌کند، نه بازیابی
بحران مستقل یا PITR را.

## صلاحیت‌سنجی خطا در مرحلهٔ 1E

در این گام، شواهد آزمون‌های قطعی و ایزوله به‌روشنی از شواهد عملیاتی زنده تفکیک شده‌اند:

- آزمون‌های ایزولهٔ اتصال‌دهنده و API، سنجهٔ قدیمی، خروجی ناقص و محدود، نبود سنجهٔ قابل‌استفاده، متن
  بدساخت و بلندتر از قرارداد و تزریق دستور در فیلدهای پایش را پوشش می‌دهند. احرازهویت منبع، متن
  نام میزبان، سنجه، مقدار، واحد یا مسئله را به «دستور» تبدیل نمی‌کند.
- اتصال زنده، نمای هشت‌سنجه‌ای خود را با دلیل `metrics_truncated` ناقص اعلام کرد؛ هر هشت سنجهٔ
  مشاهده‌شده تازه بودند. این نشان در تولید پاسخ، هش معیار شاهد، ذخیره‌سازی ماندگار، جزئیات ممیزی
  و بازیابی اجرا حفظ شد.

- با توقف کوتاه رابط HTTPS و API زبیکس، خلاصهٔ پایش و بررسی زنده، خطای امن و قابل‌تکرار `503`
  با کلید `connector.summary_unavailable` برگرداندند. اجرای شکست‌خورده و رویداد ممیزی متناظر ثبت
  شد؛ در همان زمان یک پرسش عمومی و بدون شاهد با مدل محلی پاسخ گرفت. پس از راه‌اندازی رابط، دریافت
  دادهٔ تازه بازگشت و هیچ پاسخ خام وابستگی یا اعتبارنامه‌ای وارد API نشد.
- توقف موتور Zabbix به‌تنهایی API مبتنی بر PHP را از دسترس خارج نکرد، زیرا رابط مستقیماً پایگاه
  را می‌خواند. این تفاوت مشاهده‌شده ثبت شده و به‌اشتباه موفقیت آزمون قطعی اعلام نشده است.

این نتایج فقط سناریوهای نام‌برده را می‌پوشانند و جای آزمون باقی‌ماندهٔ WAN با مرورگر جدا، انقضای
گواهی، پایان مهلت و لغو، کمبود فضا، بار پایدار، پشتیبان و بازیابی را نمی‌گیرند.

## صلاحیت‌سنجی قطع WAN و راه‌اندازی مجدد در مرحلهٔ 1F

پس از فعال‌کردن زمان‌سنج بازگشت خودکار، یک سیاست خروجی موقت و جداگانهٔ nftables روی هر چهار مهمان
اعمال شد. این سیاست رابط محلی، شبکهٔ خصوصی مصوب و IPv6 پیوند-محلی را نگه داشت و همهٔ مقصدهای دیگر
IPv4 و IPv6 را رد کرد. آزمون مستقیم اینترنت روی هر چهار مهمان شکست خورد و شمارنده‌های قاعده، بسته‌های
ردشده را ثبت کردند. SSH و مسیرهای مجاز شبکهٔ داخلی برقرار ماندند و هر چهار مهمان وضعیت `running`
با صفر واحد خراب داشتند.

هنگامی که هر چهار مهمان از WAN جدا بودند، یک نشست تازهٔ احرازهویت‌شده، پرسش‌های عمومی فارسی و
انگلیسی را بدون آمیختن محتوای Zabbix پاسخ داد. آمادگی هوش مصنوعی محلی تأیید شد و یک بررسی زندهٔ تازه،
هشت سنجهٔ تازه، نشان موردانتظار `metrics_truncated`، ذخیرهٔ ماندگار، هش مستقلِ تأییدشدهٔ شاهد و
ممیزی پیوندخورده برگرداند. بنابراین بخش سرور و API از OFF-01 و OFF-05 پذیرفته شد. OFF-03 هنوز ناقص
است، زیرا کارخواه یک نشست تازهٔ API بود، نه یک فرایند مرورگر تازه با جداسازی مستقل از WAN.

تلاش‌های نخست راه‌اندازی مجدد Zabbix به مهلت ۳۰ دقیقه‌ای systemd رسیدند. ابزار اصلاح‌شده همان تأخیر
را تکرار کرد و نقش خود را به‌عنوان علت کنار زد. گزارش بوت پیشین، رقابت واقعی را نشان داد: واحد شرکت
سازنده به سرویس صوری PostgreSQL وابسته بود و پایان مهلت توقف نداشت؛ بنابراین خوشهٔ واقعی پایگاه زودتر
خاموش می‌شد و فرایندهای باقی‌ماندهٔ Zabbix نمی‌توانستند توقف را کامل کنند. یک drop-in بازبینی‌شده
اکنون `postgresql@16-zabbix.service` را الزام می‌کند، ترتیب درست را می‌سازد و مهلت توقف را به ۹۰
ثانیه محدود می‌کند. توقف کنترل‌شده در کمتر از یک ثانیه و با پایگاه فعال پایان یافت؛ در بوت بعدی نیز
Zabbix پیش از PostgreSQL خاموش و پس از آماده‌شدن PostgreSQL راه‌اندازی شد.

پس از آن مهمان‌های اتصال، هوش مصنوعی و برنامه، یکی‌یکی و هرگز هم‌زمان، راه‌اندازی مجدد شدند. اتصال
و هوش مصنوعی بدون اصلاح بازگشتند. بوت نخست برنامه همان نقص سرویس صوری را آشکار کرد: فرایند API بالا
آمد، اما خوشهٔ PostgreSQL خاموش ماند. drop-in برنامه با الزام `postgresql@16-nextops.service` این
وابستگی را اصلاح کرد و در تکرار آزمون، پایگاه پیش از API آماده شد. در هر راه‌اندازی پذیرفته‌شده، سیاست
موقت قطع WAN پیش از شبکهٔ عادی بار شد، مهمان با وضعیت `running` و صفر واحد خراب بازگشت، سرویس‌های
نقش خود و ورود تازه و پاسخ عمومی دوزبانه یا هشت سنجهٔ تازه را گذراند و سپس همهٔ فایل‌های موقت حذف و
HTTPS مستقیم برقرار شد. بررسی ماندگار نهایی پس از بوت برنامه نیز موفق بود. بنابراین بخش سرور و API
از پذیرش راه‌اندازی مجدد آفلاین و سالم پذیرفته شد. کارزار بعدی
`stage1-completion-20260922-01` زیرآزمون مرورگر تازه را نیز بست.

## صلاحیت‌سنجی زندهٔ مرحلهٔ دو

در ۱۴۰۵/۰۷/۰۱ یک نشست تازهٔ Microsoft Edge فقط به مبدأ خصوصی برنامه دسترسی داشت؛ پراکسیِ
مسدودکننده، WAN را می‌بست و اعتبارسنجی عادی TLS فعال بود. بررسی تازهٔ رخداد به انگلیسی برای مقصد
`app` و به فارسی برای مقصد `ai`، منشأ ترکیبی Zabbix/Linux و شناسه‌های تازه و ماندگار اجرا، شاهد و
ممیزی را برگرداند. چیدمان موبایل راست‌به‌چپ، خروج، الزام ورود در برگهٔ تازه و نبود درخواست بیرونی
از برنامه نیز پذیرفته شد.

تلاش نخست پس از ۳۰ ثانیه HTTP `504` گرفت، درحالی‌که llama.cpp هنوز در حال تولید بود. مسیر
`/api/v1/incidents/investigate` در محل ۱۸۰ثانیه‌ای و محدودشدهٔ دستیار در Nginx نبود و به مهلت
پیش‌فرض ۳۰ثانیه‌ای می‌افتاد. پروفایل نسخه‌دار و آزمون ایستای آن اصلاح شدند، `nginx -t` پیش از
بارگذاری مجدد موفق بود و سپس دروازهٔ کامل مرورگر زنده دو بار، از جمله پس از reboot ماشین‌ها،
پذیرفته شد.

برای آزمون بازیابی وابستگی، پیش از توقف اتصال‌دهندهٔ فقط‌خواندنی یک زمان‌سنج پنج‌دقیقه‌ایِ
راه‌اندازی خودکار فعال شد. مسیر رخداد خطای امن و بومی‌شدهٔ `503` با کد
`dependency_unavailable` داد، اما پرسش عمومی از هوش مصنوعی محلی پاسخ `200` گرفت. پس از بازگشت
`/healthz` اتصال‌دهنده، پایش و بررسی تازهٔ ترکیبی با شناسه‌های ممیزی ماندگار موفق شدند. زمان‌سنج
پاک شد و اتصال‌دهنده در پایان فعال بود.

سپس Zabbix، اتصال‌دهنده، هوش مصنوعی و برنامه یکی‌یکی reboot شدند. در هر اجرای پذیرفته‌شده، شناسهٔ
بوت تغییر کرد، سرویس‌ها و سلامت محلی نقش بازگشت، وضعیت `running` شد، شمار واحد خراب صفر بود و نشان
نیاز به reboot باقی نماند. زمان بازیابی اتصال‌دهنده، هوش مصنوعی و برنامه به‌ترتیب ۱۵٫۱۰۹، ۲۹٫۰۳۱
و ۱۹٫۵۳۱ ثانیه بود. کاوشگر نخست Zabbix نام واحد PostgreSQL و محل گوش‌دادن وب را اشتباه تعریف کرده
بود؛ خوشهٔ واقعی `postgresql@16-zabbix`، شنوندهٔ Zabbix و رابط TLS با CA معتبر در بررسی اصلاح‌شده
موفق شدند، بنابراین زمان ساختگی برای Zabbix گزارش نمی‌شود. در پایان، یک بررسی دوزبانهٔ تازه در
مرورگر روی کل سامانهٔ راه‌اندازی‌شده موفق بود.

## لایه‌های آزمون

| لایه | شاهد مورد نیاز |
|---|---|
| واحد | قواعد دامنه، سیاست قطعی، دامنهٔ دسترسی و اعتبار آرگومان |
| یکپارچگی PostgreSQL | migration، قیدها، کار ماندگار، اجارهٔ کار، تأیید اتمی و بازیابی |
| قرارداد MCP | آغاز ارتباط، schema ابزار، هویت، لغو، خطا و خروجی محدود یا ناقص |
| شبیه‌ساز اتصال | عیب‌یابی تعریف‌شده و خطای صریح قابلیت ناموجود، بدون اطلاعات ورود واقعی |
| API و مرورگر | ورود، مجوز، پیشرفت و اتصال دوباره، صفحه‌بندی و هر دو جهت متن |
| امنیت | تزریق، تعویض مقصد، پالایش رمز، دور زدن درگاه و بازپخش تأیید |
| پایداری | توقف، کار تکراری، دیسک پر، قطع ممیزی یا پایگاه یا مدل و نتیجهٔ نامشخص راه دور |
| آفلاین | دارایی و مدل و ورود و بازیابی محلی و عملیات LAN مجاز بدون اینترنت |
| CPU و بار | بار ترکیبی محدود، توزیع تأخیر و سقف منابع روی سخت‌افزار تأییدشده |
| بازیابی و انتشار | تمرین restore، سازگاری نسخه و schema و شرایط بازگشت |

رفتار PostgreSQL با خود PostgreSQL آزموده شود، نه با جایگزین راحت SQLite. حالت پیش‌فرض شبیه‌ساز است. آزمون آزمایشگاهی یا عملیاتی مجوز صریح و ثبت نسخهٔ فروشنده می‌خواهد. پاسخ mock اثبات کارکرد API تجهیز نیست.

## سناریوهای مخرب الزامی

دستور پنهان در لاگ یا راهنما یا شرح ابزار، شواهد خارج از سازمان و محیط، مقصد غیرمجاز، تزریق فرمان و SQL، خطای دارای رمز، تأیید جعلی یا منقضی یا تکراری، تغییر آرگومان و مقصد و وضعیت اولیه پس از تأیید، لغو نقش، کار تکراری، دور زدن درگاه، تغییر DNS یا redirect، خروجی خراب مدل، توقف اتصال‌دهنده، نبود ممیزی و لغو یا timeout پس از تغییر احتمالی پوشش داده شوند.

نتیجهٔ سیاست و عدم اجرا سنجیده شود، نه صرفاً متن مؤدبانهٔ رد درخواست. صفر بودن اجرای غیرمجاز در مجموعهٔ مشخص، شرط انتشار است؛ تضمین ناممکن بودن همهٔ حملات آینده نیست. پوشش یا کنترل دسترسی برای سبز شدن آزمون تضعیف نشود.

## مجموعهٔ ارزیابی دوزبانه

سناریوهای ساختگیِ نسخه‌دار فارسی، انگلیسی و ترکیبی شامل رخداد Linux، شبکه، firewall، پایگاه داده و ESXi، نام مبهم، شاهد ناکافی، متن مخرب و مرز تأیید یا رد ساخته شوند. دادهٔ توسعه از ارزیابی مستقل جدا و تعداد نمونه ثبت شود. شناسهٔ منبع و فرمان اجرایی دست‌نخورده بمانند. بازبینی متخصص حوزه و فارسی‌زبان لازم است. داور خودکار اختیاری، محلی و CPU-only است و تنها مرجع تصمیم نیست.

درستی ابزار و آرگومان، تصمیم مجوز، نرخ ادعای بی‌شاهد، ارجاع شاهد، کیفیت بازیابی، بازیابی پس از خطا، روانی فارسی، schema، انتظار صف، زمان نخستین توکن و تأخیر کامل اندازه‌گیری شوند. میانگین خوب نباید شکست فاجعه‌بار یک ردهٔ اقدام را پنهان کند.

## گزارش شواهد

هر گزارش شامل commit، فرمان، تعداد آزمون، شکست و skip، نسخهٔ داده و مدل، هویت سخت‌افزار و محیط اجرا، اندازه‌گیری، محدودیت و روش بازتولید پالایش‌شده است. نمونهٔ خام کارایی در صورت ایمن بودن نگه داشته شود. هدف با مشاهده، سلامت با شبیه‌سازی و شبیه‌سازی با آمادگی عملیاتی اشتباه نشوند.
